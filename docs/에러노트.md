# 2026-08-15 — 외교백서 ETL 첫날

## 1. 옛날 한글 파일(HWP 3.0)의 글자가 깨졌다

**무슨 일이**
압축은 풀렸는데(366,999바이트) 글자가 전부 깨졌다. 그런데 **글꼴 이름은
멀쩡했다** — "신명조", "중고딕", "휴먼명조" 는 읽히는데 본문만 쓰레기.

**왜**
글꼴 이름은 **정순**으로, 본문은 **역순**으로 저장돼 있었다.
2바이트 글자를 저장할 때 앞뒤가 뒤바뀌어 있었던 것이다.

**어떻게 고쳤나**
"미국" 이라는 낱말을 조합형으로 인코딩해서, 그 바이트열이 파일에 있는지 찾아봤다.

```
'미국' 정순 바이트  →  0회
'미국' 역순 바이트  →  164회   ← 여기 있다
```

읽을 때 두 바이트를 뒤집어서 읽도록 바꿨더니 5,596자 → 61,092자가 됐다.

**배운 것**
깨진 데이터를 볼 때 **"내가 아는 낱말이 바이트로는 어떻게 생겼는지"** 를 만들어
파일에서 찾아보면 된다. 추측하지 말고 검색하면 답이 나온다.

## 2. 문서에 없는 한자가 나왔다 — 폰트가 거짓말을 한다

**무슨 일이**
2003년 문서에 `리펑(㤚鵬)` 이라고 나왔다. `㤚` 는 실제로 쓰이지 않는 희귀 한자다.
2008년엔 `영변핵시설폐쇄₩봉인` 처럼 원화 기호가 끼어 있고,
2021년엔 `Trans-Paci䞺c Partnership` 이라고 나왔다.

**왜**
PDF 폰트가 **글자 그림을 엉뚱한 번호에 넣어놨다.** 화면에는 `李` 로 보이지만
컴퓨터가 읽으면 `㤚` 가 나온다. 사람 눈과 기계 눈이 다른 것을 본다.

| 뽑힌 것 | 실제 | 연도 |
|---|---|---|
| `㤚` | `李` | 2003·2004 |
| `₩` | `·` 가운뎃점 | 2008·2009 |
| `䞺` | `fi` (합쳐 쓴 글자) | 2021 |
| `쇼` | `▲` | 2017 (OCR) |

**어떻게 고쳤나**
교정표를 파일로 만들었다 (`config/text_repairs.tsv`). **근거를 함께 적었다.**

```
㤚 → 李   근거: 2003·2004 리펑(㤚鵬)·리자오싱(㤚肇星) — 모두 李
```

코드에 박지 않고 파일에 둔 이유는, 새 손상이 나올 때마다 **근거와 함께**
한 줄 늘리는 자리가 필요해서다. 근거 없는 치환은 넣지 않는다.

**배운 것**
PDF 에서 뽑은 글자를 그대로 믿으면 안 된다. **빈도 상위에 이상한 글자가
보이면 폰트 문제를 의심**한다. 그리고 고칠 때는 왜 그렇게 고쳤는지 남긴다.

## 3. 눈으로 똑같은데 컴퓨터는 다르다고 한다 — 호환용 한자

**무슨 일이**
`李` 를 옮겨 적었는데 원문에 없다고 나왔다. 복사해서 붙여넣어도 안 맞았다.

**왜**
`李` 가 **두 종류** 있다.

```
李  U+674E   일반
李  U+F9E1   호환용     ← 눈으로 구별 불가
```

옛날 문서 호환 때문에 유니코드에 같은 글자가 두 번 들어가 있다.

**어떻게 고쳤나**
`unicodedata.normalize("NFC", 글자)` 한 줄. 호환용을 일반으로 바꿔준다.
가운뎃점도 같은 문제였다 — `·` `・` `∙` `･` `‧` `․` `ㆍ` 가 전부 다른 글자다.

**배운 것**
**"눈으로 같은데 안 맞는다"** 면 유니코드 정규화를 먼저 해본다.
한글 문서에서는 특히 가운뎃점과 한자를 조심한다.

## 4. 공백이 통째로 사라진 해가 있다

**무슨 일이**
2003년 문서가 이렇게 나왔다.

```
쟝쩌민전국가주석만당및국가중앙군사위주석에유임되고
```

**왜**
그 시기 PDF 는 띄어쓰기를 글자 사이 간격으로만 표현하고 **공백 문자를
넣지 않았다.** 공백률이 8%였다(정상은 20~50%).

**어떻게 고쳤나**
대조할 때 **양쪽의 공백을 전부 지우고** 비교하도록 했다.
띄어쓰기는 판본마다 흔들리는 정보라 잃어도 엄밀함이 떨어지지 않는다.

**배운 것**
문자열을 비교할 때는 **무엇을 무시할지 먼저 정한다.** 그리고 그 규칙을
비교하는 양쪽에 똑같이 적용한다. 한쪽에만 걸면 비교가 무의미해진다.

## 5. 연도로 규칙을 만들면 반드시 예외가 나온다

**무슨 일이**
"2020년부터는 좌우 펼침 PDF" 라고 알고 있었는데, 2004·2010·2015·2016·2018년도
펼침이었다. 게다가 **2015년은 1장만 단면이고 2~7장이 펼침**이었다.

**왜**
발간 담당자가 해마다 달랐고 정해진 규칙이 없었다.

**어떻게 고쳤나**
연도로 판단하지 않고 **파일을 열어 쪽 폭을 재서** 판정했다.

```
쪽 폭 > 700pt  →  펼침. 반으로 자른다
```

**배운 것**
**"몇 년부터는 이렇다" 는 규칙은 깨진다.** 데이터를 열어서 직접 재는 쪽이
언제나 낫다. 규칙은 사람이 만들고 데이터는 그 규칙을 안 지킨다.

## 6. 똑똑하게 고치려다 본문을 10~30% 날렸다 ⚠

**무슨 일이**
쪽 옆에 세로로 붙은 머리글이 본문 문장 사이로 끼어들었다.

```
인쇄된 것:  ②국제협력 증진 및 국가이미지 제고
뽑힌 것:    ②국제협력  국제  증진 및 국가이미지 제고
                       ↑ 머리글 조각
```

"좁고 긴 덩어리는 세로쓰기니까 버리자" 고 필터를 넣었다.

**왜**
그 조건에 **본문 문단도 걸렸다.** 2018·2020~2025년 글자 수가 10~30% 사라졌고
2005년 인용문 3건이 문장 중간에서 끊겼다.

**어떻게 고쳤나**
검증기가 잡았다.

```
2005     3    실패 3
  2005-1  quote 가 원문에 없다
```

되돌리고 `formats.py` 에 **왜 안 되는지** 적어뒀다. 그 자리는 인용에서 `(…)` 로
끊어 표시한다.

**배운 것**
**개선이라고 생각한 것이 파괴일 수 있다.** 그래서 "고치기 전에 검증부터
세운다" 는 순서가 중요하다. 검증이 없었으면 조용히 넘어가서, 나중에
"왜 인용이 안 맞지?" 하며 한참 헤맸을 것이다.

## 7. 같은 실수를 한 번 더 했다 — 쪽번호 살리려다 망침

**무슨 일이**
2022~2024년은 쪽번호가 머리글과 한 줄에 붙어 있었다.

```
008 제1장 2022년 국제정세 및 외교정책 기조
```

숫자를 떼고 비교하면 머리글로 인식되겠다고 생각했다.

**왜**
**본문 줄에서도 숫자가 떨어져 나갔다.** 서로 다른 문장이 같은 줄로 묶여
지워졌다. 쪽번호는 오히려 줄었고(2020년 352→175) 인용문 2건이 깨졌다.

**어떻게 고쳤나**
또 검증기가 잡았다. 되돌리고 `dehead.py` 에 사유를 적었다.

**배운 것**
**6번과 같은 유형의 실수를 반복했다.** 둘 다 "머리글을 더 지우려다" 본문을
잃었다. 지우는 쪽으로 손대는 것은 위험하다는 걸 한 번 겪고도 또 했다.

→ 그래서 계획서에 **"한 해씩 통과시키고 넘어간다"** 규칙을 넣었다.
   28개년을 다 뽑고 나서 발견하면 전부 다시 뽑아야 한다. 실제로 **세 번** 그랬다.

## 8. PowerShell 로 파일 고치다 한글이 깨졌다 (내 실수)

**무슨 일이**
`extract.py` 의 버전 번호 한 줄을 바꾸려고 이렇게 했다.

```powershell
(Get-Content scripts\extract.py) -replace '...' | Set-Content -Encoding utf8
```

파일 전체 한글이 깨졌다. `_RE_APPENDIX = re.compile(r"遺濡?)` 같은 상태가 됐다.

**왜**
`Get-Content` 가 파일을 **시스템 기본 인코딩(ANSI)** 으로 읽고,
`Set-Content` 가 **UTF-8** 로 썼다. 읽을 때 이미 깨진 것을 다시 저장했다.

**어떻게 고쳤나**
파일 전체를 다시 썼다. 그 뒤로는 파일 수정에 **전용 편집 도구**를 쓰고
셸 텍스트 치환은 쓰지 않는다. 꼭 써야 하면 `-Encoding UTF8` 을 읽을 때도 붙인다.

**배운 것**
**한글 파일을 셸 명령으로 고치지 않는다.** 인코딩이 조용히 바뀐다.
그리고 이런 사고는 커밋이 돼 있으면 되돌리기 쉽다 — 자주 커밋할 이유다.

## 9. 표의 칸이 하나 밀렸는데 아무도 몰랐다

**무슨 일이**
2016·2021년 상태가 `blocked` / `no-section` 이어야 하는데 `pending` 으로
나왔다. 화면에서는 "아직 안 함" 으로 보일 상황이었다.

**왜**
표(TSV)에서 **탭 하나가 모자랐다.** 값들이 한 칸씩 밀려서
`blocked` 가 `markStyle` 칸에 들어앉고 `status` 는 비어버렸다.
사람 눈으로는 절대 안 보인다.

**어떻게 고쳤나**
**아는 값만 통과시키는 검사**를 넣었다.

```
status 는 verified / partial / pending / blocked / no-section 중 하나여야 한다
아니면 → "칸이 밀렸을 수 있다" 며 빌드 중단
```

넣자마자 또 하나 잡혔다 — `flags` 칸에 설명문을 넣어놨던 것.

**배운 것**
**빈칸과 잘못된 값은 다르다.** "이 칸에 올 수 있는 값" 목록을 만들어두면
칸 밀림이 그 자리에서 잡힌다. 표 형식 데이터에서 가장 흔한 사고다.

## 10. 30년 전 스캔본은 한자가 전멸했다

**무슨 일이**
1989년 백서를 OCR 했더니 한글은 잘 읽는데 이렇게 나왔다.

```
짧시조"89 ※파을  /  %투프 구현  /  조.랫밴로  /  훼※빼가
```

**왜**
그 시절 백서는 **국한문 혼용**인데, 설치한 OCR 이 **한국어만** 알고 있었다.
한자 자리를 억지로 한글로 읽으려다 쓰레기가 됐다.

**어떻게 고쳤나**
한자(중국어) 인식을 함께 켰다.

```
kor 만        →  짧시조"89 ※파을
kor+chi_tra   →  實用主開的 接近含   (실용주의적 접근을)
```

완벽하진 않지만(`主開` 는 `主義` 가 맞다) 쓰레기 → 읽을 수 있는 수준이 됐다.
대신 **2.3초 → 6초** 로 느려졌다.

**배운 것**
OCR 은 **무슨 글자가 나올지 미리 알려줘야** 제대로 읽는다.
그리고 옛날 문서를 다룰 때는 그 시대의 표기법을 먼저 확인한다.

→ 우회하지 않고 사용자에게 알렸다. 다른 셸로 다시 시도하니 됐다.

# 2026-08-15 (저녁) — 전문 ETL 파일럿

## 12. 문단으로 나눌 수 없는 문서였다

**무슨 일이**
백서를 문단 단위로 뽑으려 했더니 4,615개 중 **98%가 100자 미만**이었다.
한 문장이 세 조각으로 잘렸다.

```
[46자] Rupo) 총리와 정상회담을 갖고, 양자 차원의 호혜적 협력 증진, 개발협력 분야를
[45자] 비롯한 국제무대에서의 공동 협력 강화, 한반도 및 유럽 지역정세 평가 및 지역 공
[43자] 동체 구축 과정에서의 벨기에의 경험 공유 방안 등에 대해 심도있게 협의하였다.
```

**왜**
"빈 줄 = 문단 경계" 로 잡았는데, PDF 추출본은 **줄마다 빈 줄이 들어간다.**
그래서 모든 줄이 문단이 됐다.

PDF 가 스스로 묶어둔 '블록' 을 써봤지만 **이 PDF 는 블록도 줄 단위**였다
(4,550개 중 99%가 100자 미만). 이 문서들에는 문단 경계가 **아예 기록돼
있지 않다.**

**어떻게 고쳤나**
문단을 포기하고 **문장**으로 갔다. 한국어 공문서는 `…하였다.` 로 규칙적으로
끝나서 경계가 분명하다. 결과: 1,775개 · 중앙 112자.

**배운 것**
**데이터에 없는 구조를 뽑아낼 수는 없다.** 원하는 단위가 원본에 기록돼 있는지
먼저 확인한다. 그리고 문장 단위는 오히려 지식그래프에 낫다 — 한 문장이 한 주장이다.

## 13. 쪽 단위로 자르니 문장이 끊겼다

**무슨 일이**
`…실질적 진전을 이룩함` 에서 끝났다. 다음 쪽으로 이어지는 문장이었다.

**왜**
쪽마다 따로 문장을 나눴다. 쪽 경계를 문장 경계로 착각한 셈이다.

**어떻게 고쳤나**
**파일 전체를 이어붙인 뒤** 문장을 나누고, 각 문장이 시작한 글자 위치로
어느 쪽인지 되짚었다.

**배운 것**
자르는 단위와 저장하는 단위는 다를 수 있다. 자를 때는 크게 보고,
기록할 때 잘게 되짚는다.

## 14. 부록을 통째로 잃을 뻔했다

**무슨 일이**

**왜**
부록은 **표**다. `…하였다.` 로 끝나지 않는다.

```

```

**어떻게 고쳤나**
부록은 문장이 아니라 **줄 단위**로 뽑았다. 2,241개를 건졌다.
그리고 `단위` 칸을 만들어 `문장` 과 `표줄` 을 구별했다.

**배운 것**
**한 가지 규칙으로 문서 전체를 처리하려 하면 안 된다.** 본문·표·목차는
성질이 다르다. 다르게 다루고, 무엇으로 다뤘는지 데이터에 남긴다.

## 15. 정규식 하나가 10분을 잡아먹었다

**무슨 일이**
목차를 뽑는 정규식을 넣었더니 프로그램이 **10분이 지나도 안 끝났다.**
전에는 몇 초였다.

**왜**
```
^\s*(.{4,60}?)\s*[.·…\s]{2,}\s*(\d{1,3})\s*$
                      ↑ \s 가 앞뒤 \s* 와 겹친다
```
겹치는 부분이 있으면, 안 맞는 긴 줄을 만났을 때 컴퓨터가 **모든 조합을
다 시도한다.** 경우의 수가 폭발한다(catastrophic backtracking).

**어떻게 고쳤나**
겹침을 없애고(`\s` 를 빼고 점선 문자만 요구), 긴 줄은 아예 건너뛰게 했다.
다시 몇 초로 돌아왔다.

**배운 것**
정규식에서 **`\s*` 옆에 `\s` 를 넣지 않는다.** 그리고 규칙을 넣기 전에
"안 맞는 경우" 를 먼저 생각한다. 맞는 경우는 대개 빠르다.

## 17. 검사기가 한글 전체를 "깨진 글자"라고 했다 (내 실수) ⚠

**무슨 일이**
최종 점검이 이렇게 세웠다.

```
오류  깨진 글자   483,078개 / 793,610자 (60.9%)
```

그런데 "깨진 글자"로 뽑아준 표본은 **완전히 멀쩡했다.**

```
발 간 사 2002년도는 북한 핵문제가 다시 대두되고…
```

**왜**
검사기에 이렇게 썼다.

```python
BAD_CHARS = re.compile(r"[㐀-䶿豈-﫿㄰-㆏]")
```

`豈` 를 **호환용 한자(U+F900)** 라고 생각하고 썼는데, 실제로 입력된 것은
**일반 한자(U+8C48)** 였다. 둘은 눈으로 구별되지 않는다.

그래서 범위가 `U+8C48 ~ U+FAFF` 가 됐고, 그 사이에 **한글 전체
(U+AC00~U+D7A3)** 가 들어가 있었다.

**어떻게 고쳤나**
글자 대신 **코드로** 썼다.

```python
BAD_CHARS = re.compile("[㐀-䶿豈-﫿㄰-㆏]")
```

**배운 것**
**이 노트 3번에 "눈으로 똑같은데 컴퓨터는 다르다"고 적어놓고, 그걸 잡으려고
만든 검사기에서 똑같이 당했다.**

정규식 범위에 한자·특수문자를 **글자 그대로 쓰지 않는다.** 반드시 `\uXXXX`
코드로 쓴다. 눈으로 확인할 수 없는 것은 손으로 쓰면 안 된다.

그리고 — **거짓 경보를 낸 검사기는 진짜 문제보다 위험하다.** 60% 라는 숫자를
믿었다면 멀쩡한 파이프라인을 뜯어고쳤을 것이다. 검사기가 이상한 숫자를 내면
데이터를 의심하기 전에 **검사기를 먼저 의심한다.**

## 23. 마침표 뒤 공백은 좌표로 알 수 없었다

**무슨 일이**

```
2005년   문장 1,140 → 512개 (-55%)   중앙 71 → 184자
정답지   4/4 → 1/4
```

문장이 사라진 게 아니라 **서로 이어붙었다.**

**왜**
좌표를 재보니 이랬다.

```
낱말 사이   '를'→'위'  +0.272
마침표 뒤   '다.'→'또'  -0.268   ← 오히려 겹친다
```

이 글꼴은 마침표를 다음 글자에 바짝 붙여 조판한다. **좌표에는 신호가 없다.**

**어떻게 고쳤나**
국문 조판 규칙을 썼다 — 한국어는 낱말 안에 마침표를 넣지 않는다. 그래서
**문장부호 '앞'이 한글이면 그 부호 뒤는 띄운다.**

처음엔 부호 '뒤'를 봤다가 틀렸다. `있습니다.2005년에` 처럼 숫자가 이어지는
자리를 놓쳤기 때문이다. 앞을 보니 전부 갈렸다.

```
'…있습니다.2005년'   앞이 '다' → 띄운다    ✓
'9.19'  '2005.12'    앞이 숫자 → 그대로    ✓
'Rev. Kim'           앞이 로마자 → 그대로  ✓
```

**배운 것**
**측정할 수 없는 것은 규칙으로 메운다.** 다만 그 규칙이 무엇을 건드리고
무엇을 안 건드리는지 예시로 못박아 둔다. '앞'과 '뒤' 중 어느 쪽을 보느냐로
결과가 완전히 달라졌다.

## 25. 기준선이 '내용'이 아니라 '조판'을 재고 있었다

무시하게 된다.

## 26. 같은 실수를 두 번째로 했다 — 한자 인식이 새 파이프라인에 안 옮겨졌다

**무슨 일이**
1989~1996년 스캔본 OCR 이 예상보다 3배 빨랐다. 좋아할 일이 아니었다.

```
예상   쪽당 6초
실제   쪽당 2.0초   ← 왜 빠르지?
```

설정을 열어 보니 이랬다.

```python
OCR_LANG = "kor"      # ← 한자가 없다
```

**10번 항목에서 이미 겪고 고친 문제였다.**

**왜**
그때 고친 것은 **옛 파이프라인**(scripts/extract.py)이었다. 전문 추출용으로
scripts/lib/ocr.py 를 새로 만들면서 **그 교훈이 따라오지 않았다.**

에러 노트에는 적혀 있었지만, 코드에는 옮겨지지 않았다.

**어떻게 고쳤나**

```python
OCR_LANG = "kor+chi_tra"
```

곁들여 두 가지를 더 손봤다.

```
1) find_tessdata 가 'kor+chi_tra.traineddata' 를 찾고 있었다
   → '+' 로 갈라 언어팩이 전부 있는 폴더를 고른다

2) 캐시 이름이 파일 지문뿐이었다
   → 언어를 바꿔도 예전 결과가 그대로 돌아온다. 하마터면 한자를 켜 놓고
     한글만 읽은 결과를 다시 받을 뻔했다
   → 이름에 'kor+chi_tra-300-psm6' 을 붙였다
```

확인:

```
kor 만        →  짧시조"89 ※파을
kor+chi_tra   →  (附錄)  外交關係 樹立 現況  地域別 現況
```

**배운 것**
**빨라졌으면 의심한다.** 느려질 이유가 없는데 빨라졌다면 무언가를 건너뛰고
있는 것이다. 이번엔 "3배 빠르다"가 유일한 단서였다.

그리고 — **에러 노트는 코드로 옮겨져야 산다.** 도구를 새로 만들 때는 옛
도구에서 무엇을 배웠는지 먼저 훑는다. 노트에만 적혀 있으면 같은 구덩이에
다시 빠진다.

**캐시 이름에는 '무엇으로 만들었나'를 넣는다.** 재료가 바뀌면 캐시도 달라야 한다.

## 27. 빈 폴더 하나가 밤샘 작업을 5시간 반 세웠다

**무슨 일이**
아침에 로그를 보니 이랬다.

```
[01:30]  끝난 연도: 2/8
[02:00]  끝난 연도: 2/8
[03:00]  끝난 연도: 2/8      ← 숫자가 안 변한다
[07:00]  끝난 연도: 2/8      ← 6시간째
```

01:30 에 멈춰 있었다. 오류 메시지는 이것뿐이었다.

```
[ERROR] etl_test\1990 이 이미 있다. --force 를 붙여라.
```

**왜** (세 겹이었다)

첫째, **폴더는 일을 시작할 때 만들어진다.** 끝났을 때가 아니다. 그래서
'폴더가 있다'는 '했다'가 아니라 '하다 말았을 수도 있다'였다.

둘째, **'이미 했다'는 판단 뒤의 행동이 틀렸다.** 건너뛰고 다음 해로 가야
하는데 프로그램 전체를 멈췄다. 1990 하나 때문에 1991~1996 여섯 해가
같이 날아갔다. 한 해씩 돌릴 때 쓰라고 만든 안전장치를 여덟 해를 한 번에
돌리는 데 그대로 썼다.

셋째, **아무도 안 지켜봤다.** 밤샘 스크립트는 '1996이 끝나기를' 기다리기만
했지, 그쪽이 죽었는지는 몰랐다.

**어떻게 고쳤나**

```
1) '끝났다'의 기준을 폴더 → meta.json 으로 바꿨다
   폴더만 있으면 '하다 말았다'로 보고 조용히 치우고 다시 한다

2) 한 해가 실패해도 다음 해로 간다. 그리고 두 바퀴 돈다 —
   첫 바퀴에서 못 읽은 파일이 남으면 한 번 더 시도한다

3) 감시견(watchdog.sh)을 붙였다. 5분마다 확인해서 죽어 있으면 되살린다
   일부러 죽여서 시험했다 — 5분 만에 되살아났다
```

**배운 것**
**"시작했다"와 "끝냈다"를 같은 표시로 나타내면 안 된다.** 중간에 끊길 수
있는 일이라면 반드시 '끝났다'는 표시를 따로 남긴다.

**숫자가 안 변하는 것도 신호다.** 진행률이 여섯 시간 동안 2/8 이었는데
아무도 이상하게 여기지 않았다. 감시는 '죽었나'뿐 아니라 '나아가고 있나'도 본다.

## 28. 기준선이 스스로를 가뒀다

**무슨 일이**
37개년을 다 뽑고 마지막 점검을 돌렸더니 27개년이 한꺼번에 빨간불이었다.

```
2020년   오류  기준선  chars 483,969→251,519 (-48%)
2022년   오류  기준선  chars 476,658→232,773 (-51%)
...
오류가 있는 해 27개 — 고치기 전에는 다음으로 넘어가지 않는다.
```

**왜**
글자가 사라진 게 아니었다. 어제 **재는 방법을 바꿨다.** chars 를 '공백 포함'
에서 '공백 제외'로 고쳤는데, 저장된 기준선은 옛 방법으로 잰 값이었다.
**자가 바뀐 것을 물건이 바뀐 것으로 읽었다.**

여기에 함정이 하나 더 있었다.

```
기준선이 안 맞음  →  '오류'
오류인 해는       →  기준선을 새로 저장하지 않음
                  →  영원히 안 맞음
```

**스스로를 가두는 고리**였다.

**어떻게 고쳤나**
기준선에 **'어떻게 쟀는지'의 판 번호**를 함께 적는다.

```python
METRIC_VERSION = 2   # 1: 공백 포함 / 2: 공백 제외
```

판이 다르면 '오류'가 아니라 '미완'으로 둔다 — 비교할 수 없는 것이지
틀린 것이 아니다. 그러면 새 기준선을 깔 수 있고 고리가 풀린다.

**배운 것**
**재는 방법을 바꾸면 눈금에 판 번호를 남긴다.** 안 그러면 데이터가 멀쩡한데
경보가 울리고, 헛경보가 몇 번 나면 진짜 경보도 무시하게 된다.

그리고 — **검사가 스스로를 고칠 길을 막으면 안 된다.** '틀렸다'와
'비교할 수 없다'는 다른 상태다. 섞으면 빠져나올 수 없다.

## 29. 같은 파일이 이름만 바꿔 두 번 들어 있었다

**무슨 일이**
2004년만 유난히 자료가 적었다. 원본을 열어 보니 이랬다.

```
2005 외교백서 제1장.pdf   파일 지문 1e1b46379c0b
2005 외교백서 제2장.pdf   파일 지문 1e1b46379c0b   ← 완전히 같은 파일
2005 외교백서 제3장.pdf   첫 줄이 "CHAPTer 2"     ← 이름과 내용이 어긋난다
```

배포된 자료 자체가 그랬다. 우리 데이터에 **1장 내용이 두 번** 들어가 있었다.

**왜**
파일 이름만 보고 골랐다. 이름이 다르면 다른 파일이라고 믿었다.

**어떻게 고쳤나**
파일을 고를 때 **내용의 지문(sha256)** 을 보고 같은 것은 하나만 쓴다.
그리고 건너뛴 사실을 meta.json 에 적어, 검사가 '누락'과 '일부러 건너뜀'을
구별하게 했다.

```
! 2005 외교백서 제2장.pdf 은 2005 외교백서 제1장.pdf 와 같은 파일 — 건너뛴다
```

**원본은 지우지 않았다.** 배포된 자료를 우리가 손댈 일이 아니고, 거르는 일은
파이프라인이 할 몫이다.

**배운 것**
**이름을 믿지 말고 내용을 본다.** 특히 남이 만든 자료를 받아 쓸 때 그렇다.

그리고 — **자료가 유난히 적은 해는 반드시 원본을 열어 본다.** '2004년은 원래
적은가 보다' 하고 넘어갔으면 두 번 세어진 통계를 그대로 썼을 것이다.

## 30. 고치면 숫자가 달라지는데, 기준선은 그것도 오류라 한다

**무슨 일이**
중복을 걸러냈더니 2004년 숫자가 줄었다. 당연한 일인데 검사가 세웠다.

```
오류  기준선  sentences 454→276 (-39%)
```

**의도한 변화**인데 통과할 방법이 없었다. 기준선을 새로 깔려 해도, 오류인 해는
기준선을 저장하지 않는다.

**어떻게 고쳤나**
`--accept` 를 만들었다. **기준선 말고 다른 오류가 없을 때만** 그 해의 기준선을
새로 깐다.

```
python scripts/check.py --year 2004 --accept
  → 기준선이 달라진 것을 의도한 변화로 받아들인다
```

다른 오류가 하나라도 있으면 거부한다 — 승인이 만능 열쇠가 되면 안 된다.

**배운 것**
**"틀렸다"와 "달라졌다"는 다르다.** 회귀 검사는 달라진 것을 알려주는 도구이지,
달라지면 안 된다는 규칙이 아니다. 사람이 "이 변화는 맞다"고 말할 길을 열어 두지
않으면, 결국 기준선 파일을 손으로 고치게 되고 그게 훨씬 위험하다.

## 31. 지식그래프의 '관계'가 절반 넘게 틀렸다 — 나라 나열 때문

**무슨 일이**
문장 하나에서 함께 나온 개체끼리 이어 관계를 만들었다. 종류(협력·갈등·대화·
지원)까지 붙이고 표본 24개를 원문과 대조했더니 **정확도가 33%** 였다.

```
[협력] 중국—브라질
  "미국, 일본, 중국, 러시아, 호주, 인도, 브라질 등 25여개국과 32건의
   조약을 체결함으로써 이들 나라와의 실질 협력을 강화하고"
```

한국이 **각각과** 맺은 것이지 중국과 브라질이 협력한 것이 아니다.

**왜**
외교백서는 나라를 **나열**하는 문장이 아주 많다. 한 문장에 일곱 나라가 나오면
짝이 21개 생기고, 문장에 '협력'이 있다는 이유로 21개 전부 '협력'이 된다.
틀린 라벨 12개 중 9개가 이것이었다.

**어떻게 고쳤나** (세 겹)

```
1) 관계 낱말을 문장 전체가 아니라 **두 이름 사이**에서만 찾는다
2) 두 이름 사이에 **다른 개체**가 끼면 나열로 보고 잇지 않는다
3) 두 이름 사이에 쉼표·가운뎃점·'및'·'등'이 있어도 나열로 본다
```

곁들여 두 가지를 더 잡았다.

```
'인도-태평양'의 '인도'를 인도(India)로 세고 있었다 → 지역 이름을 먼저 지운다
'테러 사태'와 '테러사태'가 따로 세어졌다(113 + 22) → 공백을 떼어 합친다
```

**결과**

```
정확도  33% → 87%  (표본 15개를 원문과 대조)
라벨률  50% →  9%  (확실한 것만 붙이니 줄었다)
```

**배운 것**
**덜 붙이고 맞히는 편이 낫다.** 다 붙이고 반이 틀리면 아무도 못 믿는다.
그래서 두 숫자를 함께 밝힌다 — "관계 1,100개 중 100개에 종류를 붙였고,
그 100개는 87% 맞다."

그리고 — **'같은 문장에 나왔다'는 관계가 아니다.** 공기(共起)를 관계로 쓰려면
그 사이에 무엇이 쓰여 있는지 봐야 한다. 이 문서처럼 나열이 잦은 글에서는
특히 그렇다.

**남은 한계**
문장의 90%가 나열이라 관계를 못 붙인다. 이건 규칙의 한계가 아니라 **자료의
성질**이다. 더 붙이려면 문장 뜻을 이해하는 모델이 필요하다.

## 32. 조사가 붙으면 이름을 통째로 못 잡고 있었다

**무슨 일이**
정권별 정책을 보여주려는데 다섯 정권이 **빈 화면**이었다. 노태우 정부의
'북방정책', 노무현 정부의 '평화번영정책' 같은 유명한 것이 하나도 없었다.

원문에는 분명히 있었다.

```
'평화번영정책' 든 문장 50개
뽑힌 것: set()      ← 하나도 못 잡았다
```

**왜**
이름 뒤에 붙는 조사를 떼려고 이렇게 썼다.

```python
r"([가-힣…]{2,12}?(?:정책|구상|…))(?![가-힣])"
                                    ↑ 여기
```

'정책' 뒤에 한글이 오면 안 된다고 해 놓고, 조사는 나중에 떼려 했다.
그런데 **'평화번영정책과'는 정책 뒤에 '과'가 오므로 매치 자체가 안 된다.**
조사 떼는 코드까지 가지도 못했다.

'북방정책 추진'처럼 뒤가 공백인 것만 잡히고 있었다.

**어떻게 고쳤나**
조사를 **패턴이 함께 먹게** 하고, 그다음에 뗀다.

```python
_JOSA_TAIL = r"(?:으로써|이라는|에서는|으로|에서|까지|의|을|를|에|와|과|은|는|이|가|…)"
r"([가-힣…]{2,12}?(?:정책|구상|…)" + _JOSA_TAIL + r"?)(?![가-힣])"
```

**결과**

```
정책        9개 → 19개
신남방정책  75회 → 159회   (두 배)
포용정책    20회 → 106회   (다섯 배)
빈 정권     5개 → 1개
```

곁들여 두 가지를 더 잡았다.

```
'신북방정책' 한 번에 '북방정책'까지 세어져, 노태우 정부 북방정책이
문재인 정부 것으로 보였다 → 긴 이름 안에 든 짧은 이름은 버린다

'인도-태평양 전략'(209회)과 '인태전략'(52회)이 갈렸다
→ 표기를 '인태' 하나로 모아 248회로 합쳤다
```

**배운 것**
**"나중에 정리하겠다"는 계획은 그 자리까지 가야 성립한다.** 조사를 떼는
코드는 멀쩡했는데, 그 앞에서 막혀 한 번도 실행되지 않았다.

그리고 — **빈 화면은 반드시 이유를 말해야 한다.** "정책 중심" 보기가 그냥
비어 있으면 고장인 줄 안다. 지금은 "이 정권 백서에 잡힌 정책 이름이
없습니다"라고 적는다. 실제로 그 한 줄을 넣으려다 이 버그를 찾았다.

## 33. 목차를 못 읽어 6개년이 통째로 비어 있었다 — 그런데 원본에는 다 있었다

**증상**
기능 2(정권별 외교정책 변화)를 만들려고 주제 묶음을 백서 목차에서
뽑으려 했다. 세어 보니 목차가 붙은 문장이 65,433개 중 43,906개(67%)뿐이고,
**여섯 해가 0% 였다.**

```
1989~1992   0.0%
2009~2012   0.3%
2020        48.6%
```

"원본에 목차가 없나 보다" 하고 주석님께 「목차 없는 6년은 빈칸으로
둘까요」를 여쭈었다. 주석님이 답했다 — **"37년 자료에 다 목차가 있어."**

**원인**
자료 문제가 아니라 **읽는 규칙이 한 가지 모양만 알아본 것**이었다.
원본을 열어보니 백서는 세 가지로 제목을 적는다.

```
① 제1절 국제 정세 개관        한 줄        ← 이것만 알고 있었다
② 제1절                      두 줄로 나뉨
   국제 정세 개관                          2003·2009~2025년, 507줄
③ 第1節 世界의 主要情勢        한자         1989~1992년, 451줄
```

②가 특히 나빴다. 제목 없는 `제1절` 을 만나면 `sectionTitle = None` 으로
**앞서 잡아둔 제목까지 지워버렸다.** 그래서 2009~2012년이

```
절 번호   98% 붙음
절 제목    0% 붙음     ← 같은 함수가 같은 줄에서 정한 값인데 갈렸다
```

라는 이상한 모양이 됐다. 이 어긋남이 없었으면 "원본에 목차가 없다"고
믿고 넘어갔을 것이다.

**어떻게 찾았나**
`제N절` 이라는 글자가 2009~2012년 본문에 81~248개씩 **실제로 있다**는
것을 먼저 셌다. 규칙 자체를 따로 떼어 돌려보니 잘 잡혔다. 그렇다면
실행 중에 뭔가 다른 것이다 — 실제 쪽을 넣어 한 줄씩 따라가 보니
목차 쪽에서 잡은 제목을 뒤이은 본문 쪽이 `None` 으로 덮고 있었다.

**어떻게 고쳤나**

```python
# 한글과 한자를 함께 받는다
_MARK_SECTION = re.compile(_ORNAMENT + r"(?:제|第)\s*(\d{1,2})\s*(?:절|節|勵)…")

# 제목이 비어 있으면 다음 줄을 본다
if title is None:
    for nxt in lines[i+1:i+3]:
        if _looks_like_title(nxt): title = _clean_title(nxt)

# 제목을 못 읽었다고 앞서 잡은 제목을 지우지 않는다
if h[1] is None and h[0] == cur.get("section"):
    return cur
```

**결과**

```
1990    0.0% → 99.7%
2010    0.0% → 98.3%
2020   48.6% → 99.2%
2013   76.9% → 99.0%
1997   99.3% → 99.3%   (원래 정상. 안 망가뜨렸다는 확인)
```

**곁들여 잡은 것 — 전 연도 목차 소재 확인**
37개년을 하나씩 열어 목차가 어디 있는지 확인했다.

```
① 목차 전용 파일    17개년
② 본문 파일 안 목차쪽 16개년   (2025년은 그림이라 글자 인식 필요)
③ 목차 없음          4개년   1997·1998·1999·2000
```

1997~2000년은 파일 7~10개 전체에 `목차`·`차례`·`目次` 가 **0회** 나온다.
정말 없다. 대신 본문 제목이 깨끗해 되만들 수 있다.

**배운 것**
**"자료에 없다"와 "내가 못 읽는다"는 완전히 다르다.** 그런데 화면에는
똑같이 빈칸으로 보인다. 27번(빈 폴더가 밤샘을 5시간 반 세움)과 같은
가족이다 — 서로 다른 사정이 같은 모양으로 나타나면 반드시 헷갈린다.

그리고 — **한 함수가 같은 줄에서 정하는 두 값이 갈리면, 그 자체가 단서다.**
절 번호 98% 대 절 제목 0% 는 자연스러운 결손이 아니다. 결손률이 아니라
**결손의 모양**을 봐야 했다.

마지막으로, 주석님이 "37년 다 목차가 있어" 라고 말해주지 않았으면 나는
없는 자료를 만들어 넣는 설계를 하고 있었을 것이다. **원본을 아는 사람의
한마디가 측정보다 빨랐다.**

## 34. 변수 이름 하나가 문장을 전부 표로 바꿨다

**증상**
33번을 고치고 2010년을 돌렸더니 **문장이 0개**가 됐다. 대신 표줄이
1,000개 넘게 생겼다.

```
고치기 전   327쪽 / 1,989문장
고친 뒤     327쪽 /     0문장 / 2,831표줄
```

**원인**
제목 판별에 쓰려고 `_SENT_END` 라는 이름을 새로 만들었다. 그런데 그
이름은 **이미 문장을 자르는 규칙이 쓰고 있었다.**

```python
154: _SENT_END = re.compile(r"(?<=다\.)\s|…")   ← 문장을 자르는 자
290: _SENT_END = re.compile(r"(다|음|임|함)\s*[.]\s*$|…")   ← 내가 덮어씀
```

문장을 못 자르니 파일 하나가 통째로 한 덩어리가 되고, 길이가
`MAX_SENT_CHARS`(1,000자)를 넘어 전부 '표줄' 로 떨어졌다.

**어떻게 고쳤나**
이름을 `_TITLE_NOT_END` 로 바꿨다. 하는 일이 다르면 이름도 달라야 한다.

**배운 것**
**한 파일 안에서 이름은 공용 자원이다.** 새 이름을 지을 때 파일 안을
먼저 찾아봐야 했다. `grep _SENT_END scripts/etl.py` 한 번이면 끝날 일이었다.

그리고 — **이 사고가 30초 만에 드러난 것은 고친 직후에 숫자를 봤기
때문이다.** 네 해를 한꺼번에 돌려 '문장 0개' 를 바로 봤다. 규칙을
고쳤으면 그 자리에서 숫자를 확인한다.

## 35. 30% 줄어든 글자를 OCR 탓으로 몰았다 — 아니었다

**증상**
목차 결함을 고치고 37개년을 다시 뽑은 뒤, 묶기 도구가 경보를 냈다.

```
2017년  chars 270,524 → 190,688 (-30%)
2019년  chars 380,979 → 245,418 (-36%)
```

두 해는 하필 새로 글자 인식(OCR)을 돌린 해였다. **그래서 OCR 을 의심했다.**

**틀린 진단**
반쪽 한 장을 골라 설정만 바꿔 돌려봤다.

```
kor          공백 뺀 글자 605
kor+chi_tra  공백 뺀 글자 471    ← 지금 설정. 22% 적다
```

"한자 사전을 켜면 한글을 22% 덜 읽는다" 고 결론 내고, 주석님께
세 가지 선택지까지 드렸다. **표본이 반쪽 한 장이었다.**

**실제**
같은 비교를 2017·2019년 **전체**로 다시 했다.

```
kor          한글 317,434   공백 뺀 전체 448,349
kor+chi_tra  한글 311,901   공백 뺀 전체 439,808
차이                 1.7%                1.9%
```

22% 가 아니라 2% 였다. 그렇다면 30% 는 OCR 이 아니다.

결정적 확인 — **내 변경 직전 코드로 같은 해를 돌렸다.**

```
        기준선(밤샘)   직전 코드    내 코드
2017      270,524     196,812    196,812
2019      380,979     247,544    247,544
```

직전 코드와 내 코드가 **글자 하나까지 같다.** 원인은 밤샘 실행 뒤에
들어온 파이프라인 개선(중복 파일 제거 등)이었고, 기준선만 낡아 있었다.
1994·2001·2005·2007년이 같은 이유로 걸린 것과 **똑같은 경우**였는데,
2017·2019년만 "OCR 을 새로 돌린 해" 라는 사정이 겹쳐 눈이 흐려졌다.

**어떻게 고쳤나**
OCR 손질을 되돌리고(`git checkout scripts/lib/ocr.py`), 다른 네 해와
똑같이 기준선을 승인했다. **고칠 것이 없었다.**

**배운 것**
**표본 하나로 비율을 말하지 않는다.** 반쪽 한 장에서 22% 가 나왔으면
그것은 가설이지 결론이 아니다. 전체로 재는 데 30초 걸렸는데, 그 30초를
아끼려다 잘못된 선택지를 사람에게 내밀었다.

**"바뀐 것 옆에 있는 것" 을 범인으로 지목하기 쉽다.** 2017·2019년은
마침 OCR 을 새로 돌린 해였다. 그래서 OCR 을 봤다. 하지만 같은 경보가
난 다른 네 해는 OCR 과 무관했다 — **경보가 난 여섯 해의 공통점**을
먼저 봤어야 했다. 다른 점이 아니라.

그리고 — **"직전 코드로 돌려본다" 가 가장 싼 실험이다.** 이 한 번으로
끝날 일이었다. 30번(고치면 숫자가 달라지는데 기준선은 그것도 오류라 한다)
에서 이미 배운 것을 되풀이했다.

## 36. 기관 이름과 우선순위가 주제를 잘못 끌고 갔다

**증상**
기능 2 를 만들려고 백서 절 931개를 13개 줄기로 묶었다. 분류율이 98.8% 라
그대로 넘어갈 뻔했다. **표본 40개를 원문과 눈으로 대조하니 두 종류가 틀렸다.**

```
외교통상부 기본 혁신 방향        → 경제·통상 (틀림, 외교인프라여야 함)
開發途上國 經濟協力              → 경제·통상 (틀림, 개발협력이어야 함)
경제안보외교 및 주요국 경제외교   → 주변국·동맹 (틀림, 경제·통상이어야 함)
```

**원인**
둘 다 **열쇠말이 제목의 어디에 있는지**를 안 본 탓이다.

```
① 기관 이름 속 낱말
   '외교통상부' 안의 '통상' 이 경제·통상 줄기의 열쇠말에 걸렸다.
   기관 이름은 주제가 아니다.

② 넓은 줄기가 좁은 줄기보다 앞에 있었다
   줄기를 훑는 차례가 곧 우선순위인데, '경제·통상'(열쇠말 25개)이
   '개발협력'(열쇠말 8개)보다 앞이었다. 넓은 그물이 먼저 건져갔다.
```

**어떻게 고쳤나**

```python
# 기관 이름을 먼저 걷어낸다
_ORG = re.compile(r"외교통상부|통상교섭본부|외교부|외무부|外交通商部|外務部")
t = _ORG.sub("", title)

# 좁은 줄기를 앞에 둔다
코로나 → 한반도 → 개발협력 → 영사 → 공공문화 → 법적 → 인프라
      → 경제 → 다자 → 주변국 → 지역 → 국민 → 국제정세
```

**결과**
표본 40개 다시 대조 — 뚜렷한 오분류 0건. 애매한 것 2건
(`다자 경제 외교` 는 다자로 가도 경제로 가도 말이 된다).

**곁들여** — 띠 색을 밝기로 재어 보니 이웃한 두 띠(주변국·동맹 ↔ 지역외교)의
밝기 차가 6뿐이었다. 가장 큰 띠 둘이 붙어 보인다. 36으로 벌렸다.
**색은 눈으로만 고르지 말고 숫자로도 재야 한다.**

**배운 것**
**분류율은 정확도가 아니다.** 98.8% 는 "어딘가에 붙었다" 는 뜻이지
"맞게 붙었다" 는 뜻이 아니다. 붙은 것 중에 틀린 것을 세려면 표본을 뽑아
원문과 대조하는 수밖에 없다. 31번(공기(共起)를 관계로 착각)과 같은 가족이다 —
**세기 쉬운 숫자가 알고 싶은 숫자를 대신하게 두면 안 된다.**

그리고 — **규칙의 차례가 곧 규칙이다.** 열쇠말 목록만 보고는 무엇이 어디로
갈지 알 수 없었다. 훑는 차례를 바꾸자 같은 목록이 다른 답을 냈다.

## 37. 관계 종류가 8%밖에 안 붙은 까닭 — 네 가지가 겹쳐 있었다

**증상**
지식그래프의 선 1,415개 중 종류(협력·갈등·대화·지원)가 붙은 것이 110개(8%).
선을 그어놓고 그 선이 무슨 뜻인지 92%는 모르는 상태였다.

**원인 — 짝 판정 22,524회를 왜 버렸는지 세었다**

```
나열 표시(쉼표·및·등)   33.6%   ← 일부러. 표본으로 확인하니 옳다
이름을 못 찾음         18.4%   ← 결함
사이에 다른 개체        18.0%   ← 일부러
붙음                   9.4%
관계말 없음             9.0%
개체 5개 이상            4.7%   ← 일부러
너무 멂                4.4%
관계말 겹침             2.4%   ← 버릴 일이 아니었다
```

**결함 ① 별칭으로 찾고 대표 이름으로 되찾았다**

문장에서 `국제연합` 을 찾아 `유엔` 으로 저장해 놓고, 관계를 읽을 때
`text.find("유엔")` 로 되찾으려 했다. 원문에 없으니 -1 이 나온다.

```python
found = {"유엔"}              # 대표 이름
text  = "…국제연합 총회…"      # 원문은 별칭
text.find("유엔")  → -1       # 관계를 통째로 버림
```

이름이 아니라 **찾은 자리**를 넘기도록 고쳤다. 4,136회가 되살아났다.

**결함 ② 관계말이 둘 이상이면 무조건 포기했다**

`대화+협력` 처럼 두 말이 걸리면 알 수 없다고 보고 버렸다(531회).
그런데 두 이름 **가까이** 있는 말이 그 짝을 설명한다. 가장 가까운 것을
고르되, 거리가 같으면 여전히 답하지 않는다.

**결함 ③ 이름이 이름을 품은 짝**

```
우크라이나 — 우크라이나전쟁    함께 88회
유엔 — 유엔해양법협약         함께 58회
이라크 — 이라크사태          함께 21회
```

사건·조약 이름에 나라 이름이 들어 있으니 언제나 함께 나온다. 아무것도
말해주지 않는 선이다. 7개를 걷어냈다. 다만 **같은 종류끼리는 남겼다** —
인도—인도네시아는 진짜 두 나라다.

**결함 ④ '모른다' 와 '섞여 있다' 를 같이 버렸다**

한 종류가 60% 를 넘지 못하면 통째로 버렸다. 그래서 이런 짝이 '종류 없음'
이 됐다.

```
미국—북한   대화 45 · 갈등 31 · 협력 28 · 지원 11
북한—유엔   갈등 43 · 협력 34 · 대화 17 · 지원 15
```

근거가 없어서가 아니라 **정말로 섞여 있어서** 우세하지 않은 것이다.
미국과 북한의 관계는 실제로 대화와 갈등을 오간다. 셋으로 갈랐다.

```
확정  한 종류가 60% 이상        실선
혼재  근거 8개 이상인데 안 갈림   점선 + '대화·갈등 섞임'
모름  근거 자체가 모자람         옅은 선
```

**곁들여 잡은 것 — '인도적' 이 나라 인도로 잡혔다**

표본 20개 검사에서 오류 3건이 나왔는데 그중 2건이 이것이었다.

```
"【인도】적 구호활동 등…"   → 유엔—인도 '지원'
"【인도】적 차원에서…"      → 북한—인도 '지원'
```

'인도' 로 시작하는 말 3,578회 중 838회(23%)가 나라 인도가 아니었다
(인도적 670 · 인도주의 98 · 인도양 66 · 인도차이나 4).
**찾을 때만 가리고 보여줄 문장은 원문 그대로** 두었다 — 근거로 내놓을
문장이 ○○○ 로 보이면 안 된다. 가리는 글자는 길이를 맞춰
글자 자리가 밀리지 않게 했다(관계는 자리로 읽는다).

**결과**

```
              전          후
관계          1,415개     1,400개   (헛 관계 7개 제거)
확정            110개       145개
혼재              —         31개
모름          1,305개     1,224개
표본 20개 정확도  85%        95%
아는 사실 채점  18/18      18/18
```

**남은 87%는 줄일 수 없다 — 그것이 사실이다**

```
근거 0개      882개 (63%)   ← 함께 나오지만 사이에 관계말이 없음
근거 1~2개    302개 (22%)   ← 문턱 미달
근거 3개 이상  216개 (15%)   ← 여기서 176개를 붙였다 (81%)
```

문턱을 1로 낮춰 보니 `싱가포르—카자흐스탄 협력 x1` 같은 헛것이 들어왔다.
**근거만 있으면 81%를 붙인다. 문제는 63%가 근거가 아예 없다는 것이고,
그 대부분은 나열 문장이다.** 이건 방법의 한계가 아니라 자료의 성질이다.

**배운 것**
**"못 한다" 와 "안 한다" 와 "섞여 있다" 는 다 다르다.** 셋을 한 칸에
넣으면 92% 가 '모름' 으로 보인다. 나누고 나니 실제로 모르는 것이
무엇인지 보였다.

그리고 — **버리는 이유를 세어보기 전에는 무엇을 고쳐야 할지 알 수 없다.**
33.6% 를 차지한 나열 규칙은 옳았고, 정작 결함은 18.4% 짜리였다.
큰 덩어리부터 고치려 했으면 헛수고를 했을 것이다.

## 38. 부엌만 고치고 손님상은 안 봤다 — 화면에 아홉 해가 없었다

**증상**
기능 2 를 끝내고 "다 됐다" 고 보고했다. 주석님이 **"프론트 열어봐"** 라고 해서
띄워 보니, 사이트가 **1998~2025년 28개년**만 보여주고 있었다.
파이프라인은 1989년부터 37개년을 다루는데.

```
노태우 1989~1992  4년   화면에 없음
김영삼 1993~1997  5년   화면에 없음
정권 교체 비교     8건 중 6건만 나옴
```

빠진 두 건 중 하나가 이 프로젝트에서 제일 재미있는 발견이었다 —
**김영삼→김대중(1997→98)은 정권이 바뀌었는데도 거의 안 변했다(34쌍 중 23위).
IMF 한복판이었기 때문이다.** 그 절반이 화면에서는 안 보였다.

**원인**
이 프로젝트는 층이 둘이다.

```
원본 → ETL → corpus/          ← 오늘 여기만 고쳤다 (목차 67%→98%)
authoring/ (사람이 적는 표) → data.json → 화면
```

화면은 **`authoring/` 의 손으로 적은 표만** 읽는다. 그 표가 1998년부터였다.
`extract.py` 에 이유가 주석으로 적혀 있었다 —
"1989~1997 은 전부 스캔본이라 OCR 공정이 따로 필요해 제외한다".
**그 OCR 공정은 그 뒤에 생겼다. 이유가 사라졌는데 범위는 그대로였다.**

**어떻게 고쳤나**

